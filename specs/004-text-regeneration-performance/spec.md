# Feature Specification: Text Regeneration Performance

**Feature Branch**: `004-text-regeneration-performance`  
**Created**: 2026-05-15  
**Status**: Draft  
**Input**: User description: "文字の再生成による大きな処理落ちを改善し、タイマーなどの高頻度更新用途でも使えるように、根本的な性能改善と UX 改善を行いたい。"

## Clarifications

### Session 2026-05-16

- Q: この feature で、明示的な再生成呼び出しの完了意味をどこまで変えてよいですか？ → A: 同期完了の既存経路は維持しつつ、高頻度更新向けに非同期または遅延反映の別経路も提供する。
- Q: 高頻度更新向けの非同期または遅延反映経路は、呼び出し側からどう選べるようにしますか？ → A: `RegenerateMesh()` は同期のまま維持し、非同期または遅延反映は別の明示 API で呼び分ける。
- Q: 非同期または遅延反映の別 API に対して、新しい要求が到着したとき進行中の古い準備作業はどう扱いますか？ → A: 進行中の 1 件は走らせつつ、待機中の要求は常に最新 1 件へ集約する。
- Q: 非同期または遅延反映の別 API で準備処理が失敗した場合、表示とエラー通知はどう扱いますか？ → A: 直前の完成済み表示を維持し、失敗した要求は破棄してエラーを通知する。
- Q: 準備済み結果のキャッシュが上限に達した場合、どの結果を破棄しますか？ → A: 最も長く再利用されていない結果から順に破棄する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - High-Frequency Displays Stay Smooth (Priority: P1)

タイマー、カウントダウン、スコア表示のように短い間隔で値が変わる 3D テキストでも、シーン全体の操作感を損なわずに最新値を表示できる。

**Why this priority**: この用途で処理落ちが発生すると機能全体が実用に耐えないため、最優先で改善する必要がある。

**Independent Test**: 短い数値テキストを高頻度で更新するシーンを実行し、表示の正しさと操作感を単独で確認できる。

**Acceptance Scenarios**:

1. **Given** タイマー表示が短い間隔で連続更新されている状態で、**When** 1 分間継続して動作させると、**Then** 最新値が読み取れる状態を保ち、更新が原因の大きな引っかかりが発生しない。
2. **Given** 新しい更新要求が前の更新完了前に到着した状態で、**When** 表示内容が確定すると、**Then** 最終的に最も新しい値が表示され、古い値が後から上書きしない。
3. **Given** 要求された値が現在の見た目と同一である状態で、**When** 更新要求を受け付けると、**Then** 重い再生成は行われず現在の表示を維持する。
4. **Given** 短い数値表示で直前更新から一部の桁だけが変わる状態で、**When** 連続更新を継続すると、**Then** 変化していない表示部分のために毎回全文字更新と同等の待ち時間が利用者に発生しない。

---

### User Story 2 - Explicit Regeneration Does Not Stall Other Work (Priority: P2)

ユーザーまたは呼び出し側が明示的に再生成を実行した際も、タイマー進行、アニメーション、入力処理、他オブジェクト更新などの周辺処理が体感的に止まらず、シーン全体が使い続けられる。既存の同期完了 API は維持しつつ、高頻度更新用途では別の明示 API から非同期または遅延反映経路を利用できる。

**Why this priority**: 現在の実装ではコストが `RegenerateMesh()` 呼び出し時に集中するため、その瞬間に他処理まで巻き込んで処理落ちすると実用性を失うため。

**Independent Test**: 再生成を繰り返し呼び出すシーンで、タイマー進行や別オブジェクトの移動・入力反応が維持されることを単独で確認できる。

**Acceptance Scenarios**:

1. **Given** タイマー表示の再生成を短い間隔で明示的に呼び出している状態で、**When** 同時に別オブジェクトの移動やアニメーションを動かすと、**Then** 再生成呼び出しのたびに他処理が目立って停止しない。
2. **Given** 1 つのテキストオブジェクトで重い再生成を実行している状態で、**When** 他のテキストオブジェクトや非テキスト処理も同時に更新されると、**Then** それらの処理が一律に詰まらず継続する。
3. **Given** 再生成要求が連続して発生する状態で、**When** ユーザー入力やゲーム進行が同時に発生すると、**Then** 進行中の 1 件を除く待機要求は最新 1 件へ集約され、最新表示への追従を維持しつつ入力受付や進行更新が破綻しない。

---

### User Story 3 - Repeated States Return Quickly (Priority: P3)

一度表示した内容と見た目の組み合わせが再び必要になった場合、ユーザーは待ち時間をほとんど感じずにその状態へ戻せる。

**Why this priority**: タイマーやカウンターは似た表示を繰り返しやすく、再利用できる状態を素早く出せるかが実用性を左右するため。

**Independent Test**: 以前に表示した値へ戻す操作を含む更新シナリオを実行し、初回より短い待ち時間で再表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 以前に表示した値と同じ内容・同じ見た目が再度要求された状態で、**When** 表示を切り替えると、**Then** 初回表示より短い待ち時間で同じ見た目に戻る。
2. **Given** 文字内容は同じでも見た目に影響する設定が変更された状態で、**When** 表示を更新すると、**Then** 古い再利用結果ではなく変更後の見た目で表示される。
3. **Given** 長時間連続で更新し続けた状態で、**When** 一定時間後の更新を観測すると、**Then** 開始直後より極端に遅くならない。

---

### User Story 4 - Heavy Work Degrades Gracefully (Priority: P4)

計算量が大きい文字列や更新バーストが発生しても、表示は破綻せず、最新状態へ向かって安定して追従する。

**Why this priority**: 根本改善だけで吸収できない負荷の山に対しても、ユーザー体験を壊さない振る舞いが必要なため。

**Independent Test**: 複数オブジェクトへ同時に更新を集中させ、表示の一貫性と破綻しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** 新しい表示の準備に時間がかかっている状態で、**When** まだ次の表示が完成していないと、**Then** 直前の完成済み表示を維持し、空白や中途半端な表示に切り替わらない。
2. **Given** 短時間に大量の更新要求が集中した状態で、**When** 処理が追いつかないと、**Then** すべての途中状態を必ず見せることよりも、全体の操作感と最新値の反映が優先される。
3. **Given** 複数の 3D テキストが同時に更新されている状態で、**When** 1 つのオブジェクトに重い更新が発生すると、**Then** 他のオブジェクトの更新まで一律に停滞しない。
4. **Given** 非同期または遅延反映の準備処理が失敗した状態で、**When** 失敗が確定すると、**Then** 直前の完成済み表示を維持したまま失敗した要求は破棄され、利用者が失敗を認識できる通知が行われる。

### Edge Cases

- カウントダウンが短時間に複数値をまたぐ場合、途中値の一部を省略しても最終的な最新値が正しく表示される必要がある。
- ポーリングやバインディングの都合で同一内容の更新要求が繰り返し届く場合でも、重複処理で性能が悪化してはならない。
- 非同期または遅延反映の別 API に更新要求が連続到着した場合、待機キューが古い要求で肥大化してはならない。
- 非同期または遅延反映の別 API で準備処理が失敗した場合、表示が空になったり壊れたりせず、失敗要求だけを安全に破棄できなければならない。
- 準備済み結果キャッシュが上限に達した場合、新しい結果を保持するために最も長く再利用されていない結果から順に破棄できなければならない。
- フォント、サイズ、字間、輪郭、配置など見た目に影響する設定変更後は、以前の結果をそのまま再利用してはならない。
- 空文字列への更新は、高頻度更新の途中で発生しても安全に表示を消去できる必要がある。
- 複数のテキストオブジェクトが同時に高頻度更新される場合でも、1 つのオブジェクトの負荷が全体停止に波及してはならない。
- 長大な装飾テキストは正しく表示される必要があるが、タイマー用途向けの応答目標は短い表示を対象とする。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、タイマー、カウンター、スコア表示などの高頻度更新テキストについて、最新値の視認性とシーン全体の操作感を継続的に維持できなければならない。
- **FR-002**: システムは、各テキスト更新要求を順序付きの要求として扱い、より新しい要求がある場合に古い要求の結果で表示が巻き戻ってはならない。
- **FR-003**: システムは、要求された状態が現在表示中の見た目と同一である場合、重い再生成処理を回避しなければならない。
- **FR-004**: システムは、同一セッション中に同じ文字内容と同じ見た目設定の組み合わせが再度要求された場合、以前に準備済みの結果を再利用できなければならない。
- **FR-005**: システムは、文字内容、フォント、サイズ、字間、輪郭、配置など見た目を左右する入力が変化した場合、再利用可能な結果を無効化しなければならない。
- **FR-006**: システムは、数値の一部だけが変わる高頻度更新に対応し、変化していない表示部分のために毎回全文字更新と同等の待ち時間や負荷を利用者へ発生させないようにしなければならない。
- **FR-007**: システムは、新しい結果を準備中であっても、空文字列への更新を除き、直前の完成済み表示を維持しなければならない。空白表示や部分的に欠けた表示へ切り替わってはならない。
- **FR-008**: システムは、更新要求が処理能力を上回る場合、すべての途中状態の表示よりも、全体の応答性と最新要求への追従を優先しなければならない。
- **FR-009**: システムは、要求内容が空文字列になった場合、古い文字を残さず速やかに表示を消去しなければならない。
- **FR-010**: システムは、既存の同期完了再生成経路または同等の明示的な再生成操作が実行された場合でも、再生成対象以外の入力処理、タイマー進行、アニメーション、他オブジェクト更新への影響を限定し、シーン全体を一律に停止させてはならない。
- **FR-011**: システムは、明示的な再生成が連続して発生する場合でも、再生成対象以外の処理が一括で足止めされないことを検証可能な形で観測・評価できなければならない。
- **FR-012**: システムは、長時間のタイマー運用やカウンター運用でも性能劣化が累積しにくく、再利用用の保持データが実用上無制限に増え続けないようにしなければならない。
- **FR-013**: システムは、再利用された表示結果についても、同一状態から新規生成した場合と視覚的に同一の結果を出さなければならない。
- **FR-014**: システムは、複数のテキストオブジェクトが同時更新される場合でも、1 つの重い再生成が他オブジェクトすべての更新停止を引き起こさないようにしなければならない。
- **FR-015**: システムは、既存の同期完了再生成経路を後方互換の対象として維持しなければならない。既存呼び出し側は、従来どおり呼び出し復帰時点で反映済みの結果を利用できる。
- **FR-016**: システムは、高頻度更新用途向けに、既存の同期経路とは別の明示 API として非同期または遅延反映の再生成経路を提供しなければならない。この経路では、完成済みの直前表示を維持したまま、準備完了後に最新結果へ切り替えられなければならない。
- **FR-017**: システムは、非同期または遅延反映の再生成経路において、進行中の準備作業を 1 件だけ維持し、待機中の要求は常に最新 1 件へ集約しなければならない。古い待機要求を順番にすべて処理してはならない。
- **FR-018**: システムは、非同期または遅延反映の再生成経路で準備処理が失敗した場合、直前の完成済み表示を維持しなければならない。失敗した要求は破棄し、利用者または呼び出し側が失敗を観測できる通知を行わなければならない。
- **FR-019**: システムは、準備済み結果キャッシュが上限に達した場合、最も長く再利用されていない結果から順に破棄しなければならない。キャッシュ満杯を理由に新しい結果の登録を恒久的に拒否してはならない。

### Key Entities *(include if feature involves data)*

- **Text State Request**: 次に表示したい文字列値と、その見た目を決める設定群をまとめた 1 件の更新要求。要求順序の管理対象となる。
- **Display Result Signature**: 既存結果を安全に再利用できるかを判定するための識別情報。文字内容と見た目に影響する設定の組み合わせを表す。
- **Prepared Display Result**: すでに生成済みで、同じ署名が再度要求された際に即座に表示へ使える完成結果。
- **Regeneration Impact Window**: 明示的な再生成呼び出しの開始から表示反映までの間に、周辺処理へどの程度の影響が出るかを観測する評価区間。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 基準シーンにおいて、12 文字以内のタイマー表示を 1 秒あたり 10 回、60 秒連続で明示更新しても、観測区間の 95% 以上で更新起因の停止が 50 ms を超えない。
- **SC-002**: 基準シーンにおいて、明示的な再生成を 1 秒あたり 10 回実行しながら別オブジェクトの移動、入力受付、タイマー更新を同時に行った場合、周辺処理の 95% 以上で停止または遅延が 50 ms を超えない。
- **SC-003**: 同じ見た目の過去表示が再度要求された場合、95% 以上の試行で 1 回の表示更新以内に再表示される。
- **SC-004**: 1 秒間に 20 件の更新要求が到着するバースト試験で、最終表示が最新要求と一致する確率が 100% であり、その後に古い値へ巻き戻らない。
- **SC-005**: 10 分間連続のタイマーまたはカウンター運用後も、10 分時点の更新レイテンシ中央値が 1 分時点の中央値に対して 10% 以内の差に収まる。
- **SC-006**: 5 個のテキストオブジェクトをタイマー相当の頻度で同時更新した場合、可視更新の 90% 以上が要求から 100 ms 以内に反映される。
- **SC-007**: 非同期または遅延反映の準備失敗を含む試験において、失敗した要求では 100% の試行で直前の完成済み表示が維持され、失敗要求が誤って表示へ反映されない。
- **SC-008**: キャッシュ上限到達を含む試験において、新規結果の登録後も再利用機能が継続し、破棄対象が最も長く再利用されていない結果から選ばれることを 100% の試行で確認できる。

## Assumptions

- 主対象は、タイマー、ストップウォッチ、カウンター、スコア表示、簡易ステータス表示などの短文から中程度の長さのテキストである。
- 現行実装と同様に、表示更新は明示的な再生成操作または明示的な API 呼び出しを契機として行う前提とする。
- 既存の `RegenerateMesh()` 相当の同期完了経路は残し、高頻度更新用途では別の明示 API で非同期または遅延反映を選べる前提とする。
- 非同期または遅延反映の別 API は、進行中の 1 件を除く保留要求を最新 1 件へ集約する前提とする。
- 非同期または遅延反映の別 API で失敗した要求は自動再試行せず、直前表示維持と失敗通知を優先する前提とする。
- 準備済み結果キャッシュの上限到達時は、最も長く再利用されていない結果から順に退避対象となる前提とする。
- 更新要求が極端に集中する場合、途中値の一部が省略されても、最新値が速やかに表示され順序が破綻しないことを優先する。
- タイマー用途向けの応答目標は 32 文字以内のテキストオブジェクトを対象とし、より長い装飾的テキストは対応対象ではあるが主要な応答保証の外とする。
- 準備済み結果はセッション内で再利用できれば十分であり、プロジェクトまたはアプリケーション再起動後まで保持される必要はない。
- 見た目に影響する設定が変わらない限り、既存実装で得られる視覚品質を基準挙動とする。
