# Feature Specification: Solid Text 3D — レイアウト・フォント・パフォーマンス改善

**Feature Branch**: `002-text-layout-improvements`  
**Created**: 2026-04-20  
**Status**: Draft  
**Input**: User description: "Solid Text 3Dの追加開発を行います。テキストの配置について、原点を基準に（アッパー・ミドル・ローワー）（レフト・センター・ライト）、前後についても（フロント、センター、バック）を指定できるようにしたいです。縦書きに対応したいです。オブジェクトについて、文字列全体で一オブジェクトか、文字ごとに個別オブジェクトにするか選べるようにしたいです。フォントの指定が文字列型の名前一致になっていますが、インスペクタでアタッチできるようにしたいです。フォントファイルの拡張子を.bytesに変えることが、ユーザーの手順として複雑なので、アタッチされたフォントを自動的に.bytesにし、フォントディレクトリに配置するようにしたいです。文字列更新時、パフォーマンスが劣化します。UI要素として使用するケースも想定されるため、頻繁な変更に耐えるパフォーマンスを目指したいです。インスペクタで文字を変更する際、即時反映しようと動くため、文字入力のレイテンシが大きく体験が良くありません。改善してください。"

---

## Clarifications

### Session 2026-04-21

- Q: インスペクタでフォントをアタッチする際、どのアセット型で参照しますか？ → A: `Object` フィールドで `.ttf/.otf` を直接参照。エディタスクリプトが自動変換し、`.bytes` ファイルはユーザーに見えない形で処理する。
- Q: テキストが長い場合、自動的に折り返す機能は必要ですか？ → A: 最大幅（横書き）または最大高さ（縦書き）を指定し、超えた場合に自動折り返す。未設定時は折り返しなし（改行コードのみで制御）。
- Q: Per-Character モードでテキストが頻繁に更新される場合、子 GameObject の管理はどうすべきですか？ → A: オブジェクトプールで子 GameObject を再利用する。文字数増加時のみ生成し、減少時は非アクティブ化する。
- Q: 縦書きモードで ASCII 英数字（A-Z、0-9）が含まれる場合、どう表示しますか？ → A: 回転なし / 90度回転のどちらかをインスペクタでユーザーが選択できる。デフォルトは回転なし。縦中横は将来対応。
- Q: フォント参照方式を文字列型から `Object` フィールドに変更する際、既存 API の後方互換性はどうしますか？ → A: 即時破壊的変更 — 旧フィールドを完全削除し、コンパイルエラーで強制移行する。
- 補足: テキストアンカーは 27 択の単一ドロップダウンではなく、垂直・水平・奥行きの 3 軸を独立したフィールドとしてインスペクタに表示する。
- Q: 縦書きモードと Per-Character モードを同時に使用した場合、子 GameObject の位置計算はどうなりますか？ → A: 縦書きレイアウトエンジンが先に全文字の配置座標を計算し、その結果を各子 GameObject のローカル座標として設定する（横書き・縦書き共通の統一座標計算パス）。
- Q: Per-Character モードで自動折り返しが発生した場合、折り返し区切り文字（スペース等）に対応する子 GameObject はどう扱いますか？ → A: 折り返し区切り文字には子 GameObject を生成しない。可視文字のみ生成対象とし、非表示オブジェクトのプール蓄積を防ぐ。
- Q: テキストが空文字列（`""`）の場合、コンポーネントはどう振る舞いますか？ → A: メッシュをクリアして何も表示しない。警告・エラーフリー。空文字列は「何も表示しない」という正常な状態として扱う（UIユースケースでの初期状態等）。
- Q: フォントアセットが削除・移動されて参照が Missing になった場合、コンポーネントはどう振る舞いますか？ → A: 直前のメッシュを維持し続け、コンソールに1回だけ警告を出力する。フォント未設定（FR-012）とは区別し、Fail-Silent に近い安全な動作を優先する。
- Q: フォント変換中（.ttf → .bytes）にエディタが終了した場合、中間ファイルはどう扱いますか？ → A: 一時ファイルに書き込んでからリネーム（アトミック書き込み）。中断時は一時ファイルが残るが、次回起動時に FR-003 の再変換チェックで自動再変換される。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — フォントのインスペクタアタッチ (Priority: P1)

ユーザーがコンポーネントのインスペクタ上で直接フォントファイルをドラッグ＆ドロップ（またはオブジェクトフィールドで選択）して、フォントを指定できる。文字列型のフォント名入力を廃止し、標準的な Unity ワークフローに合わせる。

**Why this priority**: 現状の文字列名マッチングは全ユーザーが使用する基礎機能であり、摩擦が最も大きい。これを解消することで後続の機能（自動変換・パフォーマンス改善）の前提条件にもなる。

**Independent Test**: フォントフィールドにフォントアセットをアタッチすると、3D テキストがそのフォントで表示されることを単独で検証できる。

**Acceptance Scenarios**:

1. **Given** SolidText3D コンポーネントがインスペクタで表示されている状態で、**When** ユーザーが Font フィールドにフォントアセットをアタッチすると、**Then** そのフォントで 3D テキストが描画される。
2. **Given** フォントが未アタッチの状態で、**When** コンポーネントが実行されると、**Then** インスペクタに分かりやすい警告が表示され、デフォルト動作（何も描画しない）が行われる。
3. **Given** 実行時にフォントアセットが変更された場合、**When** 次フレームの更新が発生すると、**Then** 新しいフォントで再描画される。

---

### User Story 2 — フォントファイルの自動 .bytes 変換 (Priority: P2)

ユーザーが任意のフォントファイル（.ttf / .otf）をプロジェクトにインポートし、インスペクタにアタッチするだけで、.bytes 変換・指定フォルダへの配置という複雑な手順なしにフォントを利用できる。

**Why this priority**: 既存の手動 .bytes 変換フローはユーザーの導入障壁になっている。自動化することでセットアップコストをほぼゼロにできる。

**Independent Test**: .ttf ファイルを直接インスペクタにアタッチし、.bytes ファイルを手動作成せずに 3D テキストが描画されることを検証できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが .ttf または .otf フォントファイルをアタッチした場合、**When** コンポーネントが初期化（またはフォント変更）されると、**Then** 対応する .bytes ファイルが自動生成され、指定フォルダに配置される。
2. **Given** 同じフォントが既に .bytes として存在する場合、**When** コンポーネントが初期化されると、**Then** 再変換は行われず既存ファイルが再利用される。
3. **Given** 変換に失敗した場合（権限エラー等）、**When** コンポーネントが実行されると、**Then** エラーメッセージがコンソールに出力され、描画はスキップされる。
4. **Given** Prefab アセット上に SolidText3D コンポーネントが存在する場合、**When** そのフォントファイルがインポートされても、**Then** `FontAssetPostprocessor` による `_fontBytesCache` の自動設定は行われず、次回インスペクタで表示されたときに `OnValidate` 経由で自動設定される（開いているシーン内のコンポーネントのみ走査対象の制限）。

---

### User Story 3 — テキスト配置のアンカー指定 (Priority: P3)

ユーザーがテキストオブジェクトの原点に対するアンカー位置を、垂直（Upper / Middle / Lower）、水平（Left / Center / Right）、奥行き（Front / Center / Back）の 3 軸で指定できる。

**Why this priority**: 3D 空間でのテキスト配置において原点のアンカー設定は標準機能であり、UI 連携やシーン演出の制作ワークフローを大きく改善する。

**Independent Test**: 水平・垂直・奥行きの各軸を個別に切り替え、テキストが期待する位置に配置されることを単独検証できる。

**Acceptance Scenarios**:

1. **Given** 垂直アンカーが Upper、水平アンカーが Left、奥行きアンカーが Front に設定されている場合、**When** テキストが描画されると、**Then** テキストメッシュの左上前端が原点に一致する。
2. **Given** 垂直アンカーが Middle、水平アンカーが Center、奥行きアンカーが Center に設定されている場合、**When** テキストが描画されると、**Then** テキストメッシュの重心が原点に一致する。
3. **Given** テキスト内容やフォントサイズが変更された場合、**When** 再描画されると、**Then** アンカー設定は維持されたままメッシュが再計算される。
4. **Given** アンカー設定がインスペクタで変更された場合、**When** 変更が確定すると、**Then** リアルタイムでアンカー位置が更新される。

---

### User Story 4 — インスペクタ入力レイテンシの改善 (Priority: P4)

ユーザーがインスペクタのテキストフィールドに文字を入力する際、入力中はメッシュ再生成が走らず、フォーカスを外すか Enter キーを押したタイミングでメッシュが再生成される。

**Why this priority**: 現在の即時再生成は開発中の編集体験を大きく損なっており、全ユーザーが日常的に直面する問題である。

**Independent Test**: テキストフィールドに長い文字列を素早く入力し、入力遅延なく全文字が入力できることを確認できる。

**Acceptance Scenarios**:

1. **Given** インスペクタのテキストフィールドがフォーカスされている状態で、**When** ユーザーが連続してキーを押すと、**Then** 各キー入力の間にメッシュ再生成が割り込まず、入力が即時反映される。
2. **Given** ユーザーが Enter キーまたはフィールドからフォーカスを外すと、**When** その操作が行われると、**Then** 即座にメッシュが再生成される。

---

### User Story 5 — 頻繁な文字列更新に対するパフォーマンス改善 (Priority: P5)

実行時にテキストが頻繁に変更される UI 的ユースケース（スコア表示、カウントダウン、テロップ等）において、フレームレートへの影響が最小限に抑えられる。

**Why this priority**: UI 用途への対応はパッケージの適用範囲を大きく広げる。パフォーマンスが担保されないと実用的でない。

**Independent Test**: 毎フレームテキストを変更するシナリオを作成し、フレームレートへの影響を単独で計測できる。

**Acceptance Scenarios**:

1. **Given** テキストが毎フレーム変更される場合、**When** 60fps のシーンで動作させると、**Then** テキスト更新処理がフレーム時間の大半を占めず、フレームレートが維持される。
2. **Given** テキストの内容が前フレームと同一の場合、**When** 更新チェックが行われると、**Then** 不要なメッシュ再生成はスキップされる。
3. **Given** 複数の SolidText3D コンポーネントが同時に更新される場合、**When** 各フレームで処理されると、**Then** 処理が適切に分散・最適化される。

---

### User Story 6 — 文字ごとの個別オブジェクト化 (Priority: P6)

ユーザーが、文字列全体を 1 つの GameObject/Mesh とするか、各文字を個別の GameObject/Mesh とするかを切り替えられる。個別オブジェクト化することで、文字ごとのアニメーション・マテリアル制御が可能になる。

**Why this priority**: アニメーション表現や文字単位のインタラクションを実現するために必要な機能。コア機能の安定後に追加する。

**Independent Test**: Per-Character モードで 3 文字のテキストを設定し、3 つの子 GameObject が生成されることを単独で検証できる。

**Acceptance Scenarios**:

1. **Given** Per-Character モードが有効な場合、**When** "ABC" というテキストが描画されると、**Then** A・B・C それぞれに対応する 3 つの子 GameObject が生成される。
2. **Given** Per-Character モードが有効な場合、**When** 各子 GameObject のトランスフォームを変更すると、**Then** 対応する文字の位置・回転・スケールが変更される。
3. **Given** モードを Per-Character から Single-Object に切り替えると、**When** 切り替えが確定すると、**Then** 子 GameObject が非アクティブ化され（Destroy なし）、単一 Mesh として再描画される。
4. **Given** Per-Character モードかつ個別のマテリアルを設定した場合、**When** 描画されると、**Then** 各文字に異なるマテリアルが適用される。
5. **Given** Per-Character モードでテキストが "ABC" から "AB" に変更された場合、**When** 更新が行われると、**Then** 3 番目の子 GameObject は Destroy されず非アクティブ化され、次回文字数が増えた際に再利用される。

---

### User Story 7 — 縦書きテキストの対応 (Priority: P7)

ユーザーが縦書き（vertical writing mode）を有効にすると、日本語・中国語などの文字が縦方向に並んで表示される。

**Why this priority**: 日本語ユースケースでは縦書きは一般的なレイアウト要件。他の機能が安定してから実装する。

**Independent Test**: 縦書きモードで「あいうえお」を設定し、文字が縦に並ぶことを単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 縦書きモードが有効な場合、**When** 日本語文字列が描画されると、**Then** 文字が上から下へ縦方向に並び、各列内の文字はインスペクタで指定した固定の列幅を基準に水平中央揃えとなる。
2. **Given** 縦書きモードで幅の異なる文字（幅広文字・幅狭文字等）が混在する場合、**When** 描画されると、**Then** 各文字は列幅の固定値を基準に中心揃えされる（文字幅に応じて列幅が変動しない）。
3. **Given** 縦書きモードで英数字が含まれる場合、**When** 描画されると、**Then** 英数字はインスペクタの設定（回転なし / 90度回転）に従って表示される（縦中横は将来対応）。
4. **Given** 縦書きモードでアンカー指定がある場合、**When** 描画されると、**Then** アンカー設定が縦書きレイアウトに対して正しく機能する。
5. **Given** 縦書きモードで複数行（改行あり）の場合、**When** 描画されると、**Then** 行が右から左へ並ぶ。

### Edge Cases

- フォントアセットが削除・移動されたときに SolidText3D コンポーネントはどう振る舞うか？ → 直前のメッシュを維持し続け、コンソールに1回だけ警告を出力する。フォント未設定（FR-012）とは区別する。
- 最大幅/高さの指定と明示的な改行コードが混在する場合、どちらが優先されるか（両方適用）？
- Per-Character モードで自動折り返しが発生した場合、折り返し区切り文字（スペース等）には子 GameObject を生成しない。可視文字のみが生成・プール管理の対象となる。
- テキストが空文字列の場合、メッシュをクリアし何も表示しない（警告・エラーなし）。正常状態として扱う。
- 非常に長い文字列（1000 文字以上）でのパフォーマンスはどうなるか？ → **保証範囲外**。SC-002 の計測基準は 200 文字以下の標準的な文字数であり、200 文字超の動作は保証しない（将来対応の候補として記録）。
- Per-Character モード中にテキストが変更された場合、子 GameObject の増減は正しく行われるか？
- 縦書きモードと Per-Character モードを同時に使用した場合、縦書きレイアウトエンジンが全文字の配置座標を先に計算し、その結果を各子 GameObject のローカル座標として設定する。両モードは完全に同時使用可能。
- フォント変換中にエディタが終了した場合、中間ファイルは残るが次回起動時の FR-003 チェックで再変換する。アトミック書き込み（一時ファイル → リネーム）により不完全な完成ファイルの使用を防ぐ。
- Prefab アセットへのフォント自動設定は限定的である: `FontAssetPostprocessor` よる `_fontBytesCache` 自動設定は開いているシーン内のコンポーネントのみ対象となり、Prefab アセットは走査できない。Prefab にアタッチされたフォントは次回 Inspector 表示時に自動設定される（許容範囲の制限）。

## Requirements *(mandatory)*

### Functional Requirements

> **補足記法**: `b`・`c` サフィックス（例: FR-009b、FR-011b）は親 FR の補足要件を示す。カバレッジ追跡では独立した要件として扱う。

- **FR-001**: コンポーネントは、インスペクタ上の `Object` フィールドに `.ttf` または `.otf` ファイルを直接ドラッグ＆ドロップしてフォントを指定できなければならない（文字列名指定を廃止）。生成される `.bytes` ファイルはユーザーに見えない形で処理され、インスペクタに露出しない。
- **FR-002**: `.ttf` / `.otf` フォントファイルがアタッチされた場合、エディタスクリプトが自動的に対応する `.bytes` ファイルを生成し、指定ディレクトリに配置しなければならない。ユーザーは `.bytes` ファイルを手動で操作する必要がない。
- **FR-003**: .bytes ファイルが既に存在する場合、再変換をスキップし既存ファイルを使用しなければならない。
- **FR-004**: コンポーネントは垂直アンカー（Upper / Middle / Lower）、水平アンカー（Left / Center / Right）、奥行きアンカー（Front / Center / Back）をそれぞれ独立した設定項目として提供しなければならない。3 軸はインスペクタ上で個別に選択でき、単一の 27 択ドロップダウンにまとめない。
- **FR-005**: アンカー設定変更時、テキストメッシュはアンカーに合わせて再計算されなければならない。
- **FR-006**: インスペクタのテキストフィールドへの入力中はメッシュ再生成を行わず、ユーザーが Enter キーを押すかフィールドからフォーカスを外したタイミングでのみ再生成しなければならない（時間経過・タイムアウトによる自動確定は行わない）。
- **FR-007**: テキスト内容が前回と同一の場合、メッシュ再生成をスキップしなければならない（ダーティフラグ制御）。ただし、空文字列チェック（FR-015）および Missing フォントチェック（FR-016）は本要件より先に評価し、空文字列は常にダーティとして扱う（スキップ対象外）。
- **FR-008**: ユーザーは文字列全体を 1 つの GameObject/Mesh とする Single モードと、文字ごとに個別 GameObject/Mesh とする Per-Character モードを切り替えられなければならない。
- **FR-009**: Per-Character モードでは各文字の子 GameObject がアンカー計算を考慮した相対位置に配置されなければならない。
- **FR-009b**: Per-Character モードでは子 GameObject をオブジェクトプールで管理しなければならない。テキスト更新時は文字数が増加した場合のみ新規生成し、文字数が減少した場合は余剰オブジェクトを非アクティブ化（Destroy しない）して再利用する。スペース・改行コード・自動折り返し区切り文字など**不可視文字には子 GameObject を生成しない**。プール管理の対象は可視文字のみとする。
- **FR-010**: コンポーネントは縦書き（Vertical）と横書き（Horizontal）を切り替えるオプションを提供しなければならない。縦書きモードと Per-Character モードは同時使用可能であり、レイアウトエンジンが全文字の配置座標を計算後、各子 GameObject のローカル座標に設定する（横書き・縦書き共通の統一座標計算パス）。
- **FR-011**: 縦書きモードでは、文字が上から下・列が右から左に並ばなければならない。各列内の文字はインスペクタで指定した固定の列幅を基準に水平中央揃えとなり、文字ごとの幅によって列幅が変動しない。
- **FR-011b**: 縦書きモードでの ASCII 英数字の表示方式（回転なし / 90度時計回り回転）をインスペクタで選択できなければならない。デフォルトは回転なし。縦中横は将来対応とする。
- **FR-011c**: 縦書きモードの列幅はインスペクタで数値として指定できなければならない。未指定時は `MeshGenerationParams.FontSize × 1.1f` をデフォルトとする（行間余白を含む値）。ここで `FontSize` は `MeshGenerationParams` クラスの `FontSize (float)` フィールドを指す（`SolidText3DComponent._fontSize` から渡される実値）。
- **FR-012**: フォントが未設定の場合、インスペクタに警告表示を行い、メッシュ生成をスキップしなければならない。
- **FR-013**: コンポーネントは最大幅（横書き時）または最大高さ（縦書き時）を指定するオプションを提供しなければならない。指定された値を超えるテキストは自動的に折り返されなければならない。折り返しの粒度は、英語等の単語境界が明確な言語ではスペース・区切り文字を基準とした単語単位、日本語・中国語等の単語境界がない言語では文字単位とする。
- **FR-014**: 最大幅/高さが未設定（0または未指定）の場合、自動折り返しは行われず、改行コード（`\n`）のみで行を制御しなければならない。
- **FR-015**: テキストが空文字列（`""`）の場合、メッシュをクリアして何も描画しない。警告・エラーコンソール出力は行わない。Per-Character モードでは全子 GameObject を非アクティブ化する。
- **FR-016**: フォントアセット参照が Missing（削除・移動）になった場合、直前に生成したメッシュを維持し続け、コンソールに `LogWarning` を1回のみ出力する（毎フレーム出力しない）。フォントが未設定の状態（FR-012）とは区別し、メッシュクリアは行わない。フォント参照が御復（正常なアセットに再アタッチ）された場合、`_fontMissingWarningIssued` フラグをリセットし、次に Missing になった際に再度 `LogWarning` を出力する（同一セッション内の永続抑制は行わない）。
- **FR-017**: `.bytes` ファイルの生成はアトミック書き込み（一時ファイルに書き込んでから最終パスにリネーム）で行わなければならない。エディタ終了等による変換中断時に不完全な完成ファイルが使用されることを防ぐ。次回エディタ起動時に FR-003 のチェックで自動再変換する。

### Key Entities

- **VerticalAnchor**: 垂直方向のアンカー設定を表す列挙値 (Upper / Middle / Lower)。インスペクタでは独立したドロップダウンフィールドとして表示される。
- **HorizontalAnchor**: 水平方向のアンカー設定を表す列挙値 (Left / Center / Right)。インスペクタでは独立したドロップダウンフィールドとして表示される。
- **DepthAnchor**: 奥行き方向のアンカー設定を表す列挙値 (Front / Center / Back)。インスペクタでは独立したドロップダウンフィールドとして表示される。
- **WritingMode**: Horizontal（横書き）/ Vertical（縦書き）の列挙値。
- **ObjectMode**: SingleObject（文字列全体を 1 メッシュ）/ PerCharacter（文字ごとに個別 GameObject）の列挙値。
- **FontAssetReference**: インスペクタの `Object` フィールドでアタッチされた `.ttf`/`.otf` フォントファイルへの直接参照。エディタが透過的に `.bytes` 変換を行い、ユーザーには変換プロセスが見えない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: インスペクタのテキストフィールドへの連続入力において、1 文字あたりの入力遅延が体感できない（50ms 未満）レベルに収まる。
- **SC-002**: テキストを毎フレーム更新するシナリオで、60fps シーンにおけるフレームタイムへのテキスト更新処理の寄与が 2ms 未満に収まる（標準的な文字数の場合）。
- **SC-003**: テキストの内容が変わらない場合、メッシュ再生成処理が 100% スキップされる（ゼロアロケーション）。
- **SC-004**: フォントアセットをインスペクタにアタッチしてから 3D テキストが表示されるまでのセットアップ手順が、ドラッグ＆ドロップ 1 操作で完了する。
- **SC-005**: 垂直・水平・奥行き各軸の 3 値をそれぞれ独立して変更でき、すべての組み合わせでテキストバウンディングボックスの対応する頂点・辺・中心が原点に一致する。
- **SC-006**: Per-Character モードで生成された各子 GameObject が、それぞれ独立してトランスフォーム・マテリアルを制御できる。
- **SC-007**: 縦書きモードで日本語文字列が正しく縦方向にレイアウトされる。具体的には、各文字の Y 座標が前の文字より小さく（上→下方向）、列の X 座標が前の列より小さく（右→左方向）なることを自動テスト（`LayoutEngineTests.cs` 内の `ApplyVerticalLayout` テストグループ）で検証できる。

## Assumptions

- 対象 Unity バージョンは Unity 6 (6000.x LTS) であり、URP を前提とする。
- フォントの .bytes 変換はエディタ時（Editor スクリプト）に実行され、ランタイムビルド時には変換済みファイルが使用される前提とする。
- 縦書きにおける英数字の表示方式（回転なし / 90度回転）はインスペクタでユーザーが選択できる。デフォルトは回転なし（縦中横は将来対応）。
- Per-Character モードの子 GameObject 命名規則は `[親オブジェクト名]_Char_[インデックス]` とする（変更可能）。
- インスペクタ入力はフォーカス離脱または Enter 確定のみでメッシュ再生成する（時間経過による自動確定なし）。
- パフォーマンス計測は標準的な文字数（最大 200 文字程度）を基準とする。
- 既存の `SolidText3DComponent` の公開 API は、フォント参照方式の変更による旧フィールドの完全削除（即時破壊的変更）を除き、後方互換を保たない。ユーザーはコンパイルエラーにより新 API への移行が必要になる。
- .bytes ファイルの自動生成先ディレクトリは `Assets/SolidText3DFonts/` に固定とする（将来対応: エディタ設定による変更可能化）。
- .bytes ファイルの命名規則は `{assetGuid}.bytes` とし、元のフォントファイル名は包含しない。GUID による一意識別を優先する設計であり、`SolidText3DFonts/` フォルダをユーザーが直接参照することは想定しない（フォント参照は Inspector 経由のみ）。
